# 使用个人工作台

先用 `get_context` 查询总控绑定、已注册项目、当前消息和任务。读取某项任务时传 taskId；历史任务可用 `list_tasks` 查询。接口形状以工具清单和返回的 contracts 为准，不从记忆猜测 ID、版本或提交 SHA。

## 从对话到工作

咨询直接回答，信息不足时自然追问。优先从已注册项目和上下文识别目标；有歧义才请用户选择。`discover_projects` 只读发现项目，不代表授权导入或初始化仓库。

用户明确要求执行时先查询工作台项目和历史任务，无法唯一识别时向用户澄清。微信或钉钉新需求调用 `create_request`，使用本轮 sourceMessageId 和稳定的 operationId。调用 Codex App 的 `list_projects`，按工作台项目名称及仓库根目录匹配唯一 App 项目，使用 App 返回的 `projectId` 创建会话；工作台 `source.id` 与 App 项目 ID 属于不同命名空间，不直接比较。不能唯一匹配时先向用户澄清。初始提示只要求等待工作台派发；取得真实 threadId 后调用 `bind_task`，由工作台排队发送原始需求。项目没有有效关联、创建会话失败或投递回执不明时如实报告，不虚构执行成功。

后续确认或补充先识别原任务，通过 `send_task_message` 把当前 sourceMessageId 投递至原项目会话；有多个可能任务时先澄清。项目会话直接执行，主控负责核对工作台记录及执行结果并向用户汇报，不创建旧工作台执行组。
## 补充、执行与验收

渠道项目会话任务的用户补充使用 `send_task_message`；已有旧执行组任务继续使用 `supplement` 和其返回的决策契约。停止/恢复使用 `task_action`，复用 operationId，先核对上次结果。

验收使用当前 SHA 的 `get_diff`、`get_evidence` 和完成条件。执行者报告是待核实声明，不是唯一证据。实际错误给具体返工要求；需要人工判断或缺少必要证据时返回 human；不把源仓库尚未合并当作实现失败。

通过验收只会准备交付。向用户说明结果、验证、限制以及工作台生成的确认指令，不替用户批准。专项会话的关键结果由工作台通知总控汇报，无须自行向用户或其他会话重复发送。

## 回复与知识

渠道消息的最终答复自动回传，避免重复发消息。工具日志和内部分析不作为最终答复。工作台明确标记“已处理”的控制消息只需确认状态，不再调用相同动作。

交付后的可重复方法用 `skill_draft` 保存为草稿，记录适用前提和实际证据。巡检事件仅分析给定注册仓库的增量，提交位置、依据和待验证事项；不能将巡检通知当作用户授权创建修复任务。

出现不确定的操作回执时，查询任务和证据后再决定下一步。不要更换 operationId 来绕过去重，也不要通过 shell、直接数据库写入或 Web 用户令牌绕过 MCP 的权限边界。
